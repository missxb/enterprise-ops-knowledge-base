# VPC 网络规划与子网划分

## 1. 概述

VPC（Virtual Private Cloud，专有网络）是云上网络的基石。所有云资源（ECS、RDS、SLB 等）都部署在 VPC 内，VPC 的规划直接决定了网络的安全性、可扩展性和运维复杂度。本文将从 CIDR 规划、子网划分、路由设计、网络互通等维度，系统性地介绍企业级 VPC 网络规划的最佳实践。

## 2. CIDR 地址规划

### 2.1 规划原则

CIDR 规划是 VPC 设计的第一步，也是最重要的一步。一旦确定，后续修改成本极高。

**核心原则：**

1. **避免地址冲突**：不同 VPC、本地数据中心之间的 CIDR 不能重叠
2. **预留扩展空间**：为未来业务增长预留足够的地址空间
3. **统一规划**：企业全局统一规划，避免各部门各自为政
4. **合理粒度**：子网不宜过大（浪费地址）也不宜过小（限制扩展）

### 2.2 推荐 CIDR 方案

**中型企业（单 Region）：**

```
生产 VPC:   10.1.0.0/16   (65,534 IPs)
开发 VPC:   10.2.0.0/16   (65,534 IPs)
测试 VPC:   10.3.0.0/16   (65,534 IPs)
预发布 VPC: 10.4.0.0/16   (65,534 IPs)
共享服务 VPC: 10.10.0.0/16 (65,534 IPs)
```

**大型企业（多 Region）：**

```
Region A (华东):
├── 生产:   10.1.0.0/16
├── 开发:   10.2.0.0/16
└── 测试:   10.3.0.0/16

Region B (华南):
├── 生产:   10.11.0.0/16
├── 开发:   10.12.0.0/16
└── 测试:   10.13.0.0/16

Region C (华北):
├── 生产:   10.21.0.0/16
├── 开发:   10.22.0.0/16
└── 测试:   10.23.0.0/16

跨 Region 互联: 10.100.0.0/16
```

### 2.3 子网划分策略

**按功能分层：**

```
VPC: 10.1.0.0/16

公共子网（Public Subnet）- 放置对外服务:
├── 10.1.1.0/24   → AZ-a: SLB, NAT Gateway, Bastion
├── 10.1.2.0/24   → AZ-b: SLB, NAT Gateway
└── 10.1.3.0/24   → AZ-c: SLB

应用子网（App Subnet）- 放置应用服务器:
├── 10.1.11.0/24  → AZ-a: ECS/EC2 App Servers
├── 10.1.12.0/24  → AZ-b: ECS/EC2 App Servers
└── 10.1.13.0/24  → AZ-c: ECS/EC2 App Servers

中间件子网（Middleware Subnet）- 放置中间件:
├── 10.1.21.0/24  → AZ-a: Redis, MQ
├── 10.1.22.0/24  → AZ-b: Redis, MQ
└── 10.1.23.0/24  → AZ-c: Redis, MQ

数据子网（Data Subnet）- 放置数据库:
├── 10.1.31.0/24  → AZ-a: RDS Primary
├── 10.1.32.0/24  → AZ-b: RDS Standby
└── 10.1.33.0/24  → AZ-c: RDS Read Replica

管理子网（Management Subnet）- 运维管理:
└── 10.1.100.0/24 → 堡垒机, 监控, 日志
```

**按环境隔离：**

```
每个环境独立 VPC:
├── prod-vpc:     10.1.0.0/16
├── staging-vpc:  10.2.0.0/16
├── dev-vpc:      10.3.0.0/16
└── shared-vpc:   10.10.0.0/16 (监控、日志、堡垒机)
```

## 3. 路由设计

### 3.1 路由表规划

每个子网关联一个路由表，路由表定义了该子网的网络出口。

**公共子网路由表：**
```
目标                    下一跳
10.1.0.0/16            local (VPC 内部互通)
0.0.0.0/0              Internet Gateway (公网出口)
```

**应用子网路由表：**
```
目标                    下一跳
10.1.0.0/16            local
0.0.0.0/0              NAT Gateway (通过 NAT 访问公网)
```

**数据子网路由表：**
```
目标                    下一跳
10.1.0.0/16            local
(无默认路由 - 数据库不应访问公网)
```

### 3.2 NAT Gateway 设计

NAT Gateway 允许私有子网的实例访问公网（如拉取镜像、更新补丁），同时阻止公网主动访问。

**高可用设计：**

```
每个 AZ 部署一个 NAT Gateway:

AZ-a: NAT Gateway A (EIP: 47.100.1.1)
AZ-b: NAT Gateway B (EIP: 47.100.2.1)
AZ-c: NAT Gateway C (EIP: 47.100.3.1)

各 AZ 私有子网路由指向本 AZ 的 NAT Gateway
```

### 3.3 VPC Peering

VPC Peering 用于连接两个 VPC，实现跨 VPC 通信。

**配置要点：**
- 两端 VPC CIDR 不能重叠
- 双向都需要配置路由
- 不支持传递路由（A-B, B-C，A 不能通过 B 到达 C）

### 3.4 Transit Gateway

Transit Gateway 是中心化的网络枢纽，解决 VPC Peering 的 N² 复杂度问题。

```
          ┌──────────────┐
          │   Transit    │
          │   Gateway    │
          └──┬───┬───┬───┘
             │   │   │
        ┌────▼┐ ┌▼───┐ ┌▼────┐
        │VPC-A│ │VPC-B│ │VPC-C│
        └─────┘ └─────┘ └─────┘
             │
        ┌────▼──────┐
        │  本地数据中心 │ (VPN / 专线)
        └───────────┘
```

## 4. 安全组与网络 ACL

### 4.1 安全组（Security Group）

安全组是实例级别的虚拟防火墙，基于白名单机制。

**分层安全组设计：**

```
┌─────────────────────────────────────────┐
│              SLB 安全组                   │
│  入站: 80/TCP, 443/TCP (0.0.0.0/0)      │
│  出站: App-SG (允许转发到应用层)          │
├─────────────────────────────────────────┤
│              Web 安全组                   │
│  入站: 8080/TCP (仅 SLB-SG)              │
│  出站: App-SG + 公网 (补丁更新)           │
├─────────────────────────────────────────┤
│              App 安全组                   │
│  入站: 8080/TCP (仅 Web-SG)              │
│  出站: DB-SG + Redis-SG + 公网           │
├─────────────────────────────────────────┤
│              DB 安全组                    │
│  入站: 3306/TCP (仅 App-SG)              │
│  出站: 无                                 │
├─────────────────────────────────────────┤
│              Redis 安全组                 │
│  入站: 6379/TCP (仅 App-SG)              │
│  出站: 无                                 │
├─────────────────────────────────────────┤
│              堡垒机安全组                  │
│  入站: 22/TCP (办公网络 IP)               │
│  出站: 所有内网 (跳板访问)                 │
└─────────────────────────────────────────┘
```

### 4.2 网络 ACL（Network ACL）

网络 ACL 是子网级别的无状态防火墙，作为安全组的补充。

**与安全组的区别：**

| 特性 | 安全组 | 网络 ACL |
|------|--------|----------|
| 级别 | 实例级 | 子网级 |
| 状态 | 有状态 | 无状态 |
| 规则 | 仅允许 | 允许 + 拒绝 |
| 评估 | 所有规则 | 按顺序评估 |
| 默认 | 拒绝所有入站 | 允许所有 |

**建议策略：**
- 安全组作为主要防护手段
- 网络 ACL 用于子网级别的额外防护（如阻断已知恶意 IP）

## 5. 网络连通方案

### 5.1 云上与云下互通

**方案对比：**

| 方案 | 带宽 | 延迟 | 成本 | 适用场景 |
|------|------|------|------|----------|
| VPN 网关 | 受限 | 较高 | 低 | 临时互通、开发测试 |
| 专线 (Express Connect) | 高 | 低 | 高 | 生产环境、大数据传输 |
| SAG (智能接入网关) | 中 | 中 | 中 | 分支机构接入 |

### 5.2 多 VPC 互通

**企业级网络架构：**

```
                    ┌──────────────┐
                    │  共享服务 VPC  │
                    │ (堡垒机/监控) │
                    └──────┬───────┘
                           │ Transit Gateway
                    ┌──────┴───────┐
              ┌─────┤              ├─────┐
              │     │              │     │
         ┌────▼──┐  │         ┌───▼───┐ │
         │ 生产   │  │         │ 开发   │ │
         │ VPC   │  │         │ VPC   │ │
         └───────┘  │         └───────┘ │
                    │                    │
               ┌────▼────┐          ┌───▼───┐
               │  预发布  │          │  测试  │
               │  VPC    │          │  VPC  │
               └─────────┘          └───────┘
```

## 6. DNS 规划

### 6.1 私有 DNS

使用云厂商的私有 DNS 服务（阿里云 PrivateZone / AWS Route 53 Private Hosted Zone），实现内网域名解析。

**域名规划：**
```
生产环境: *.prod.internal.example.com
开发环境: *.dev.internal.example.com
测试环境: *.test.internal.example.com

服务发现:
mysql-master.prod.internal → 10.1.31.10
redis-cluster.prod.internal → 10.1.21.20
api-service.prod.internal → SLB 内网地址
```

## 7. 总结

VPC 网络规划的核心要点：

1. **CIDR 规划要长远**：预留至少 2-3 倍的扩展空间
2. **子网按功能分层**：公共层、应用层、数据层、管理层
3. **安全组按角色划分**：每个角色一个安全组，引用安全组而非 IP
4. **高可用设计**：多 AZ 部署，每个 AZ 独立的 NAT Gateway
5. **统一 DNS**：内网服务使用私有 DNS 域名
6. **文档化**：所有网络规划必须文档化，纳入版本管理
